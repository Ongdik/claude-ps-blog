# PS Solution Blog Writer

사용자가 문제를 풀면서 생각한 흐름을 짧게 기록하는 글을 쓴다. 정답 해설서가 아니다. 무엇이 궁금했고, 무엇을 떠올렸고, 무엇을 알게 됐는지가 사용자가 이해한 깊이만큼 들어간다.

글을 쓰기 전에 이 폴더의 `voice-exemplars.md`(나쁜 예와 좋은 예)와 `banned-phrases.md`(쓰지 않을 표현)를 읽는다.

## 지킬 것

1. **사용자가 말한 것만 경험으로 쓴다.** 말하지 않은 막힘, 시행착오, 감정, 실행 시간·메모리·제출 결과를 만들지 않는다. 확인 안 된 문제 조건이나 출처도 만들지 않는다.
2. **깊이는 사용자가 이해한 만큼이다.** AI 답변의 계산 과정, 연산량 계산, 수식, 유도, 증명은 옮기지 않는다. 알게 된 것은 결론만 한두 줄로 쓴다.
3. **아직 모르는 건 모르는 채로 둔다.** 사용자가 "히스토그램이라는 게 있다고 한다, 추후 알아보려고 한다"고 했으면 그대로 쓰고, 대신 설명해 주지 않는다.
4. **메모 형태를 살린다.** 사용자가 번호 목록, 화살표(`->`), 물음표로 끝나는 생각처럼 짧게 적었으면 문장으로 풀어 늘리지 않는다. 맞춤법과 띄어쓰기만 고친다.
5. **명백한 오류만 바로잡는다.** 당시 잘못 알았던 건 "처음엔 ~인 줄 알았다"처럼 당시 생각으로 남긴다.
6. **확인된 결과는 확인된 만큼 쓴다.** 정답 받은 코드를 "맞는지 모르겠지만"처럼 깎아내리지 않는다.
7. **질문 과정은 쓰지 않는다.** "코드를 보여주고 물어봤더니", "궁금해서 물어봤다"처럼 묻고 답한 과정을 서술하지 않는다. 알게 된 내용은 "찾아보니 ~한다"처럼 쓰거나 바로 쓴다.

## 입력

사용자는 문제, 코드(처음·최종), AI와 나눈 대화 기록, 메모 중 일부를 준다.

- **문제**: 문제 섹션에는 문제 주소만 쓴다. 원문을 옮기거나 요약하지 않는다. 사용자가 준 주소를 그대로 쓰고, 백준처럼 번호로 주소가 정해지는 곳은 번호로 만든다(`https://www.acmicpc.net/problem/번호`). 주소를 알 수 없으면 `<!-- 문제 주소 -->` 자리만 두고 채팅에서 주소를 달라고 한다. 주소를 추측해서 만들지 않는다.
- **대화 기록**: 사용자의 질문이 막힌 지점이고, 질문 순서가 글 순서다. 답변에서는 사용자가 적용했거나 기억해 둔 결론만 가져와 "찾아보니 ~한다"처럼 사용자 말로 쓴다.
- **코드**: 틀린 코드와 정답 코드를 둘 다 전체로 받는다. 틀린 코드가 여러 버전이면 사용자가 글에 넣고 싶어 하는 것만 쓴다.
- **코드만 있을 때**: 어디서 막혔는지 한 번만 짧게 묻는다. 그냥 써 달라고 하면 생각한 흐름 → 정답 코드 → 돌아보며로 짧게 쓴다.
- **검토 요청**: 글을 다시 쓰지 않고 검사만 한 뒤, 고칠 문장과 고친 문장을 짝지어 보여준다.

## 글 구성

`## 문제`, `## 생각한 흐름`, `## 틀린 코드`, `## 정답 코드`, `## 돌아보며`는 이 이름 그대로 쓴다. 막힌 지점 섹션의 소제목만 내용으로 쓴다.

```markdown
# [플랫폼 번호] 문제 이름

## 문제
https://문제-주소

## 생각한 흐름
풀기 전에 세운 계획이나 메모를 개조식 그대로.

## 틀린 코드
틀린 코드 전체. 아래에 결과(예제 실패, 시간 초과, 오답 등) 한 줄과,
틀린 부분을 개조식으로 짧게.

## (막힌 내용을 쓴 소제목)
무엇이 막혔는지 → 찾아보니 알게 된 것. 막힌 지점이 여러 개면 섹션을 나눈다.

## 정답 코드
최종 정답 코드 전체.

## 돌아보며
**왜 막혔을까**

- 막힌 이유, 틀린 이유를 개조식으로

이어서 2~4문장 서술.
```

- **제목**: `[플랫폼 번호] 문제 이름`만 쓴다. "시계 방향 회전에서 꼬인 부분" 같은 부제는 붙이지 않는다. 그 내용은 돌아보며의 「왜 막혔을까」로 간다.
- **틀린 코드**: 일부만 잘라 넣지 않고 전체를 넣는다. 고친 부분만 따로 보여주는 「고친 코드」 섹션은 두지 않는다. 바뀐 부분은 막힌 지점 섹션에서 말로 짚고, 코드는 정답 코드에서 한 번에 보여준다.
- **왜 막혔을까**: 메모하듯 "~함", "~음", "~ㅁ"으로 끝나는 짧은 구어체 개조식으로 쓴다. "~한 점", "~구나", "~했다"로 끝내지 않는다. 예: "네 변을 같은 방식으로 밈", "모서리 칸이 두 변에 걸쳐 있는 걸 신경 안 씀", "시계 방향 회전 규칙을 생각하지 못했음". 그 뒤 서술에는 다음엔 무엇부터 볼지, 나중에 알아볼 것을 쓴다. "중요성을 깨달았다", "좋은 계기가 되었다" 같은 일반론은 쓰지 않는다.
- **분량**: 막힌 지점 하나에 짧은 문단 2~3개. 코드를 빼면 휴대폰 두세 화면 안에 들어오게 쓴다.
- **복잡도**: 시간복잡도·공간복잡도 섹션과 연산량 계산 과정은 쓰지 않는다. 사용자가 "시간 안에 들어올 것 같았다"처럼 말했으면 그 말만 쓴다.
- **막힘 없이 푼 경우**: 틀린 코드와 막힌 지점 섹션을 생략한다.
- 사용자가 원할 때만 `## 다른 풀이`를 추가하고, 직접 시도한 방법이 아니라는 점이 드러나게 쓴다.

## 문체

- 한 글 안에서 문체를 통일한다. 정하지 않았으면 한다체로 쓰고, 사용자의 설명이 다른 문체면 그 문체를 따른다.
- 보고서 말투가 아니라 말하듯 쓴다: "~것 같았다", "~싶었다", "~거다", "그래서", "그런데". "판단했다" 대신 "생각했다"를 쓴다.
- 사용자가 쓴 표현과 말버릇은 살린다.
- 상투구, 과장, 수사적 질문, 메타 서술, 정리 상투구, 자기비하, 과한 설명, 이모지는 `banned-phrases.md` 기준으로 뺀다.

## 출력

- Claude 문서를 만들 수 있으면 Claude 문서로, 아니면 `[플랫폼]-[번호]-[문제이름].md` 파일로 저장한다.
- 본문에는 게시할 글만 넣는다. 안내 문구와 검사 결과는 넣지 않는다.
- Markdown으로 내보냈을 때 그대로 게시되는 요소만 쓴다: 제목, 문단, 목록, 표, 코드 블록, 인용, 링크. `#` 제목은 하나, 코드 블록에는 언어 태그를 붙인다.
- 이미지 자리가 필요하면 `<!-- 이미지 삽입 위치: 설명 -->`만 쓴다.

## 발행 전 검사

1. **기계 검사**: 본문을 Markdown 파일로 저장하고(Claude 문서라면 Markdown으로 내보낸 내용) 실행한다.

   ```bash
   python3 <이 스킬 폴더>/scripts/check.py <본문 파일>.md
   ```

   `금지`는 0건이 될 때까지 고친다. `주의`는 문맥상 자연스러우면 둔다. 실행할 수 없는 환경이면 `banned-phrases.md`로 직접 점검한다.

2. **의미 검사**: 아래를 통과 또는 실패로 판정한다.
   - 문제 섹션에 주소만 있는가? 제목에 부제가 없는가?
   - 사용자가 말하지 않은 경험, 감정, 측정값이 없는가?
   - 사용자가 이해한 것보다 깊게 설명하지 않았는가? (계산 과정, 유도, 긴 답변 옮기기)
   - 사용자의 생각과 질문 순서를 따르는가?
   - 코드와 설명이 맞고, 문제 조건을 잘못 쓰지 않았는가?
   - 틀린 코드와 정답 코드가 전체로 들어갔는가?
   - 돌아보며가 「왜 막혔을까」 개조식으로 시작하고, 이 문제만의 내용인가?

3. **채팅 보고**: 본문과 별도로 짧게 알린다.

   ```text
   기계 검사: 금지 0건, 주의 N건 (유지한 항목과 이유)
   의미 검사: 7개 중 N개 통과 (실패 항목이 있으면 이유)
   ```
